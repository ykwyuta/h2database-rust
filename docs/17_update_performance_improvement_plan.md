# 再測定に基づく UPDATE 性能改善案

実装内容と再測定値は[実装結果](18_update_performance_implementation.md)を参照する。

## 判断の根拠

[再測定結果](16_update_performance_remeasurement.md)では、100 万行の永続化あり・単独 UPDATE は 2,409 TPS、平均実行時間 0.406 ms だった。このうち WAL の `sync_data` が 0.343 ms（約 84%）。別行を更新する 8 並列でも 2,684 TPS にとどまり、コミット経路の直列化が残る。同一行 8 並列は行待機平均 1.951 ms、p99 43.241 ms。100 万行のチェックポイントは約 136 MB を毎回追記し、同時実行時の 4 並列 UPDATE は 2,541 → 1,526 TPS に下がった。一方、各 UPDATE は主キーで 1 行だけ取得している。

この結果により、[計測前の改善仮説](14_update_performance_additional_proposals.md)の順序を更新する。**最初に全量チェックポイントの実行頻度と書き出し量を減らし、次に WAL コミットの直列化を解く。** 同一行競合と SQL/MVCC の CPU コストは、その後に対象ワークロードを分けて扱う。以下の効果は提案であり、改善倍率の実測値ではない。

## 優先順位と実施内容

| 順位 | 改善 | 対象となる実測上の問題 | まず行う変更 | 採用判断 |
| --- | --- | --- | --- | --- |
| P0 | チェックポイントの頻度を制御 | 100 万行で約 0.5 秒、約 136 MB/回、同時更新 TPS 約 40% 減 | `sync()` とチェックポイントを分離し、デモサーバーの無条件 1 秒周期を廃止する。WAL サイズ・経過時間などでチェックポイントを起動する | 永続性を保ち、更新時 p95/p99 とファイル増加速度が改善すること |
| P1 | 差分チェックポイントと容量回収 | 全量スナップショットの追記でファイルが増え続ける | CoW ツリーの変更ページだけを永続化し、ルートとページ参照を原子的に更新する。参照されないチャンクを安全に回収する | 書き出し量が変更ページ数に従い、再起動・並列更新後も整合すること |
| P2 | WAL グループコミット | 別行 8 並列でも 2,684 TPS、WAL 同期約 0.345 ms/呼び出し | コミット順序と失敗時の状態遷移を修正した後、複数の独立コミットを 1 回の WAL 同期にまとめる | 別行の TPS が上がり、単独更新の p95/p99 と耐久性が悪化しないこと |
| P3 | 同一行待機の制御 | 同一行 8 並列の p99 43.241 ms | キー別の待機キューと公平な通知を検討し、不要な一斉起床を抑える | 同一行の p95/p99、CPU 使用量、待機回数が改善すること |
| P4 | CPU 側の UPDATE 経路 | 同期を切った診断条件では CPU/ロックの比率が上がる | 未コミット版と確定版の二重 CoW、行コピー、汎用 UPDATE 処理を個別に計測して削減する | 同期あり・なしの双方で正しさを維持し、有意な実測差が出ること |

### P0: まずチェックポイントの運用を正す

現在、[`MVStore::sync`](../crates/h2-mvstore/src/store.rs) は毎回 `checkpoint()` を呼び、[`demo/002_psql`](../demo/002_psql/src/main.rs) はこれを 1 秒ごとに起動する。`H2_SYNC_COMMIT=1` なら各更新の WAL はすでに同期されており、毎秒の全量スナップショットは更新成功の耐久性を与えるための必須手順ではない。ただしチェックポイントを止め続けると WAL と起動時の再生時間が伸びるため、単に周期処理を削除するだけでは完結しない。

まず「WAL の同期」と「スナップショット作成・WAL 切り詰め」を別 API・別ポリシーにする。デモサーバーでは、WAL のバイト数、前回からの経過時間、更新量、空き容量を見てチェックポイントを要求し、複数の要求を 1 回にまとめる。変更がないときはスナップショットを作らない。停止時の明示的 `sync()` は維持する。チェックポイント処理は実行時間、追記バイト数、WAL 残量を計測し、失敗をログに記録する。バックグラウンド処理は同期 I/O を Tokio のワーカースレッドで直接実行しない構成にする。

これは**頻度を下げる暫定策**であり、1 回約 136 MB の全量書き出し自体は P1 で解決する。運用上の上限は「チェックポイント頻度を減らした場合の WAL 容量と復旧時間」を測って決める。

### P1: 全量スナップショットを差分化する

現在の [`checkpoint`](../crates/h2-mvstore/src/store.rs) は全マップのシリアライズ済みルートを新チャンクに詰め、[`append_and_commit`](../crates/h2-mvstore/src/file_store.rs) がファイル末尾へ追記する。100 万行では 1 回の小さな更新でも約 136 MB の追記になる。**マップ単位の dirty フラグだけでは、巨大な `pgbench_accounts` マップ 1 つを毎回全量書き出す問題は残る。**

変更ページを追跡するページ単位の永続形式を設け、チェックポイントでは dirty ページ、ページ参照、ルートメタデータだけを書き込む。新ルートの耐久化を確認してから WAL の対応範囲を切り詰める。古いルートやアクティブなスナップショットが参照するページは保持し、参照が消えたチャンクだけを回収する。ファイル形式の変更は読み込み互換性と移行手順を伴うため、まず既存形式の読込みを保った新規 DB 向け実装で検証する。

既存の [`compact`](../crates/h2-mvstore/src/store.rs) は全マップを再構築してファイルを置換し、WAL をクリアする。容量回収機能としてそのまま高頻度で呼ぶ案は採らない。並列更新と同時実行した際のスナップショット境界、WAL 切り詰め、置換失敗からの復旧を先に検証する。

### P2: 正しいコミット境界を作ってからグループ化する

[`commit_wal`](../crates/h2-mvstore/src/store.rs) は `version.write()` を保持したまま WAL 追記と `sync_data` を実行する。このため別行の更新も同期待ちが直列になる。単純にロックを短くするだけでは、WAL 順序、コミット版、読み手への公開順序を崩し得る。

先に、単調で一意なコミット番号を直列化点で割り当て、**WAL 追記 → 同期成功 → 確定値の公開 → 成功応答**の関係を定義する。現状の [`Transaction::commit`](../crates/h2-mvstore/src/tx/transaction.rs) は WAL 追記前に状態を `Committed` にしてアクティブ集合から除去するため、同期失敗時の扱いを修正する必要がある。暗黙トランザクションの [`execute_with_user`](../crates/h2-sql/src/executor.rs) は現在 `tx.commit()` のエラーを返すので、その伝播を維持する。チェックポイントによる WAL 切り詰めも、永続化済みのコミット番号までに限定する。

その上で、独立したコミット要求を短い待機窓または件数上限で束ね、WAL 追記後に 1 回だけ同期し、同期完了した要求へ順序どおり応答する。**同一行の更新は行待機で直列化されるため、主な対象は別行への並列更新。** 単独更新では待機窓を設ける分だけ遅くなり得るので、即時同期への切替条件を用意する。`H2_SYNC_COMMIT=0` は耐久性の違う診断条件であり、この案の代替ではない。

### P3/P4: 高パーセンタイル遅延と CPU コストを分ける

同一行の待機は [`LockManager`](../crates/h2-mvstore/src/tx/lock.rs) の `Condvar` 一斉通知を使う。キー別待機・通知の案を試す前に、通知による再起床回数、再試行回数、タイムアウト、同一キーとランダムキーの p95/p99 を追加計測する。同じ残高に対する逐次的な `+1` 更新は意味上直列なので、ロック方式だけで別行更新と同じ並列 TPS を期待しない。

CPU 側は [`Transaction::put` と `commit`](../crates/h2-mvstore/src/tx/transaction.rs) の二重 CoW、WAL エンコード、SQL の行復号・コピーを個別に測る。同期ありの単独更新ではこれらの合計は WAL 同期より小さいため、現時点では大規模な更新専用経路を先行実装しない。高速ストレージや複数行更新で比率が変わった場合に優先度を見直す。

## 検証と採否

1. **同一条件で比較する。** [測定器](../crates/h2/examples/update_perf_probe.rs)を使い、100 万行、同期あり、同一バイナリ条件で、組み込み経路と PGWire ループバックをそれぞれ測る。単独・4・8 並列、同一キー・別キーを分け、TPS、p50/p95/p99、エラー、WAL 同期時間、コミット待機時間、チェックポイント時間・追記量を保存する。測定のばらつきを把握するため複数回反復する。旧 pgbench 値との倍率は出さず、外部比較が必要なら同じ SQL・スキーマ・接続経路で別途再測定する。
2. **P0/P1 の安全性を確認する。** チェックポイント直前・書き込み中・ヘッダ更新後・WAL 切り詰め前後で強制終了し、再起動後に成功応答済みの更新が残ることを確認する。並列更新、長時間スナップショット、容量不足、書き込みエラーも含める。WAL サイズと復旧時間の上限を記録する。
3. **P2 の安全性を確認する。** 同期エラーを注入し、失敗した要求へ成功を返さないこと、確定値が早く見えないこと、コミット番号の重複・逆転・欠落がないことを確認する。グループの一部だけ書けた場合、チェックポイントとの同時実行、複数キーの原子性、ロールバックも試す。
4. **性能の採否を分ける。** P0/P1 は更新時の高パーセンタイル遅延、チェックポイント書き出し量、ファイル成長で判断する。P2 は別行 4/8 並列の TPS を主指標にし、単独更新の遅延悪化を併記する。P3 は同一行の p95/p99、P4 は CPU 時間と割り当て量を主指標にする。改善倍率は実装後の結果だけを記載する。

実装順は **P0 → P1 → P2** を基本とする。P0 で大きな遅延スパイクとファイル成長を抑え、P1 で書き出し方式を改め、P2 で残る別行更新の上限を上げる。同一行に集中する利用が主なら P3 の計測を並行して先行させる。
