# 03. ストレージエンジン設計（Rust版 MVStore）

## 1. H2 MVStore のコアコンセプト

Java版H2の `org.h2.mvstore` は、従来の「in-place更新型B-Tree + WAL」とは一線を画す、**ログ構造化追記型（Log-Structured Append-Only）Copy-on-Write (CoW) B-Tree** です。

### 主な利点
1. **クラッシュセーフティ (Instant Crash Recovery)**:
   - 既存のページを直接上書き（in-place overwrite）せず、新しいページとして別領域に追記するため、途中で電源が断たれても直前の確定済みルート（Root Pointer）に戻るだけで済み、複雑なUNDOリカバリが不要です。
2. **高速スナップショットとロックフリーリード**:
   - ツリーのルートポインタとその時点のバージョン番号を保持するだけで、O(1) で完全な過去のスナップショットが得られます。
   - 読み取りトランザクションは一切ロックを取得せず、完全に排他されずに高速にスキャンできます。
3. **連続I/Oによる高スループット**:
   - 変更差分を「チャンク (Chunk)」と呼ばれるまとまった単位（数MB）で順次追記するため、ランダムライトを回避しディスクI/O効率が極めて高いです。

## 2. ストレージレイアウトとファイルフォーマット

単一ファイル（またはインメモリ）内に以下の構造を持ちます。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                              Header Block                              │
│ - Magic Bytes: "H2RS"                                                 │
│ - Format Version: 1                                                    │
│ - Block Size: 4096 bytes                                               │
│ - Last Valid Chunk Info: ChunkID, RootPageOffset, Version, Checksum    │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│                               Chunk 1                                  │
│ ┌────────────────────────────────────────────────────────────────────┐ │
│ │ Chunk Header: Chunk ID, Version, Page Count, Max Occupied Size     │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ Page 1 (Leaf Page): Key-Value entries                              │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ Page 2 (Branch Page): Child Page Pointers & Pivot Keys             │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ ...                                                                │ │
│ ├────────────────────────────────────────────────────────────────────┤ │
│ │ Chunk Footer: Metadata, CRC32/xxHash Checksum                      │ │
│ └────────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│                               Chunk 2 (追記)                            │
│ ...                                                                    │
└────────────────────────────────────────────────────────────────────────┘
```

### ページ（Page）構造
- **Leaf Page (葉ページ)**:
  - キーと値のペアを格納。
  - レコード長可変に対応するスロット配列（Slotted Page）レイアウト。
- **Branch Page (枝ページ)**:
  - 子ページのポインタ（ChunkID + Offset）とピボットキーを格納。
- **Page ID / Reference**:
  - `PageRef = (chunk_id: u32, offset: u32)` の64ビットで表現。メモリキャッシュ内では `Arc<Page>` に直接解決。

## 3. CoW B-Tree による更新メカニズム

キーバリューの更新・挿入時：
1. 目的のLeafページを複製（クローン）し、新キーを挿入・更新。
2. その親のBranchページも複製し、新しいLeafへのポインタで更新。
3. これをルートまで伝播させ、新しい Root Page を作成。
4. 古いページはそのまま残るため、過去のバージョンを参照しているトランザクションには一切影響を与えない。

```text
       [Root v1]                      [Root v2] (New)
        /     \                        /     \
    [B1]       [B2]       ==>       [B1]     [B2'] (New)
    /  \       /  \                 /  \      /  \
  [L1] [L2]  [L3] [L4]            [L1] [L2] [L3] [L4'] (New Modified)
```

## 4. MVCC とトランザクション管理（TransactionStore）

H2の `mvstore.tx` パッケージの設計をRustネイティブに再構築します。

### VersionedValue
各キーに対応する値は、直接の生データではなく以下のバージョン構造（`VersionedValue`）を持ちます。

```rust
pub enum VersionedValue<V> {
    /// コミット済みの確定値
    Committed {
        value: V,
    },
    /// 未コミット（トランザクション実行中）の値
    Uncommitted {
        tx_id: u64,
        value: Option<V>,       // None は DELETE を意味する
        old_value: Option<V>,   // ロールバック用、または過去バージョン読取用
    },
}
```

### トランザクションライフサイクル
1. **BEGIN**:
   - 新規トランザクションID `tx_id` を発行。
   - 現在の確定済みバージョン `read_version` を記録（Snapshot Isolationの基準点）。
2. **WRITE (Put/Delete)**:
   - 対象キーの既存エントリを確認。
   - 既に別の `tx_id` が未コミットのまま更新中であれば、**Write-Write Conflict（競合）** を検出し、直ちにエラー（OCC時）またはロック待機（Pessimistic時）。
   - `VersionedValue::Uncommitted` をセットし、自身のUNDOログ（Transaction Log）に記録。
3. **READ (Get/Scan)**:
   - 値が `Committed` の場合: そのまま読み取り。
   - 値が `Uncommitted` の場合:
     - 自身の `tx_id` であれば、未コミットの `value` を参照。
     - 他の `tx_id` であれば、`old_value` を参照（コミット前の過去状態が見えるため、リーダーは絶対に待たされない）。
4. **COMMIT**:
   - 自身の `tx_id` の未コミット値をすべて `Committed` に昇格。
   - 新しいストレージバージョンとしてチャンクをフラッシュ。
5. **ROLLBACK**:
   - 自身のUNDOログを逆順に走査し、各キーを `old_value` の状態に復元。極めて高速。

## 5. コンパクション（GC / バキューム）

追記型ストレージの課題は「古い不要ページの蓄積によるディスク肥大化」です。
MVStoreのコンパクションアルゴリズムを採用します。

1. **ライブ率（Live Ratio）の計算**:
   - 各チャンクについて、「最新のツリーから現在も到達可能なページサイズ / チャンク総サイズ」を追跡。
2. **バックグラウンド・リライト**:
   - ライブ率がしきい値（例: 50%未満）を下回ったチャンクを対象に選定。
   - そのチャンク内で「まだ生きているページ」だけを読み出し、新しい最新チャンクへと再書き込み（リロケーション）。
   - 空になった古いチャンクの領域はファイルヘッダのフリーリストに返却、またはOSのファイルホールパンチング（`fallocate` / `sparse file`）でディスク領域を即時OSへ返却。
3. **VACUUM コマンド**:
   - 手動またはスケジュールでの完全コンパクションもサポート。
