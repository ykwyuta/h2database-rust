# UPDATE 性能の追加改善案

## 対象と結論

この報告は、既存の WAL、バイナリ行形式、インデックス変更を省く更新処理を前提に、`UPDATE` の追加改善余地を整理したものです。コードを読んで得た**改善仮説**であり、新しい性能計測や改善倍率の実証は行っていません。まず更新時間を区間別に測り、次に CoW ツリーの二重更新と単一行更新の汎用処理を削減するのが妥当です。WAL の並列化は、耐久性とコミット順序を保つ設計を先に固めてから進めます。

この計測前の仮説は[再測定結果](16_update_performance_remeasurement.md)で検証した。実装の優先順位は[再測定に基づく改善案](17_update_performance_improvement_plan.md)を参照する。

既存の[100万行の評価](12_pgbench_performance_evaluation.md)では、Point Update が 1 接続で **168.67 TPS / 5.93 ms**、4 接続で **373.65 TPS / 10.70 ms** です。ただし[使用した SQL](../benchmarks/pgbench/point_update.sql)は全クライアントが `aid = 100` を更新します。この値には、ストレージ全般の書き込みコストに加え、**同じ行への競合**も含まれます。1万行時の結果との違いを、データ量だけに帰属させることはできません。また、これらの数値は既存資料からの引用であり、今回再計測していません。

## 現在の更新経路から分かること

| 箇所 | コード上の事実 | 性能上の仮説 |
| --- | --- | --- |
| 対象行の探索 | `UPDATE` は単一列の等値条件とインデックスが一致すれば prefix scan から行 ID を取得し、それ以外は `scan_visible` に進む。取得後にも行を復号し、WHERE 式を評価する。([executor.rs](../crates/h2-sql/src/executor.rs#L2594-L2644)) | 単一行更新でも汎用的な走査、式評価、配列確保が残る。複合条件や複合インデックスでは全行走査になり得る。 |
| 行の更新 | 更新行を複製し、外部キー処理、全インデックスの旧値と新値の比較、行の再シリアライズを行う。`RETURNING` がなくても更新行を `updated_rows` に保持する。([executor.rs](../crates/h2-sql/src/executor.rs#L2752-L2822)) | 制約もインデックス列の変更もない更新では、不要なカタログ探索、値の複製、アロケーションを減らせる。 |
| MVCC と CoW | `Transaction::put` は既存値を復号して未コミット値を書き、コミットでは同じキーを再取得・復号して確定値を書き直す。([transaction.rs](../crates/h2-mvstore/src/tx/transaction.rs#L68-L149), [同ファイル](../crates/h2-mvstore/src/tx/transaction.rs#L325-L369)) `MVTree::put` は変更経路を CoW で作り直す。([tree.rs](../crates/h2-mvstore/src/tree.rs#L52-L93)) | 1 行更新でツリー経路の再構築と値コピーが少なくとも 2 回発生する。データ規模に伴うツリーの深さや行サイズの影響を確認したい。 |
| WAL | `WalManager::append` はコミットごとにシリアライズ、CRC 計算、末尾への書き込みを行い、既定の `H2_SYNC_COMMIT` 設定では `sync_data` を呼ぶ。([wal.rs](../crates/h2-mvstore/src/wal.rs#L61-L87), [file_store.rs](../crates/h2-mvstore/src/file_store.rs#L96-L99)) | fsync と WAL の排他ロックが、並列更新の遅延と上限を決める可能性がある。 |
| 競合 | キー操作にはストライプロックを使い、別トランザクションの未コミット値があれば待機する。([lock.rs](../crates/h2-mvstore/src/tx/lock.rs#L7-L39), [transaction.rs](../crates/h2-mvstore/src/tx/transaction.rs#L86-L126)) | 同一 `aid` のベンチマークは行単位の直列化を強く反映する。異なるキーでの結果を別に測る必要がある。 |

## 優先順位付き改善案

### P0. 更新の時間内訳と競合を先に計測する

`UPDATE` を、対象行の探索、行の復号と式評価、制約とインデックス処理、`Transaction::put`、コミット時の再書き込み、WAL エンコード、`write_all`、`sync_data`、ロック待機に分けて計測します。計測用カウンタは無効時の負荷を抑え、性能比較には同じビルド条件を使います。`p50/p95/p99`、TPS、WAL バイト数、コミット当たりのツリー更新回数も記録します。

評価は同じスキーマとデータ量で、(1) 全員が同一キー、(2) クライアントごとに別キー、(3) 一様ランダムキーを分けます。各条件で 1/4/8 接続を測り、`H2_SYNC_COMMIT=1` と `=0` は**耐久性の違う別条件**として示します。既存資料と同じ PGWire 経由の結果に加え、組み込み API 経由の結果を取ると、ネットワークとサーバー処理の割合も見えます。

**採用判断:** 区間別時間の上位を特定してから P1〜P3 を実装する。特定の区間が支配的でなければ、大規模な設計変更を先送りする。

### P1. 単一行・非インデックス列 UPDATE の専用経路を設ける

対象を「単一テーブル、主キーまたは一意インデックスの等値条件、`FROM` なし、変更列がインデックス列・外部キー列ではない」場合に限定します。実行計画でインデックスキーと変更列番号を一度解決し、行を 1 件だけ読み、WHERE の残余条件を再評価してから更新します。インデックスの旧値・新値比較、参照先がない外部キー探索、`RETURNING` 不使用時の `updated_rows` 蓄積を省きます。該当しない SQL は現行の汎用経路に戻します。

**期待する方向:** 同じキーを更新する単一接続でも CPU 時間と割り当てを減らせる可能性があります。fsync が支配的なら効果は小さくなります。NULL、型変換、トリガー相当の将来機能、複合条件、更新対象 0 行、`RETURNING` の結果を汎用経路と一致させます。

### P2. MVCC の未コミット値から確定値への二重 CoW を減らす

現状は `put` 時に未コミット版をツリーへ挿入し、`commit` 時に確定版を同じツリーへ再挿入します。まず 1 更新あたりの `MVTree::put` 回数、コピーしたページ数・バイト数、保持する履歴長を測ります。そのうえで、トランザクションの変更を専用の保留領域に保持してコミット時に一度だけツリーへ反映する方式、または既存の可視性を維持したまま確定時のコピーを減らす方式を比較します。

**成立条件:** 自トランザクションからの読み取り、他トランザクションからの不可視性、キー競合、ロールバック、古いスナップショット、WAL 再生を保つこと。現行の版履歴は 32 件で切り詰める実装なので、同一キーを連続更新しながら長時間スナップショットを開く試験も必要です。([versioned_value.rs](../crates/h2-mvstore/src/tx/versioned_value.rs#L79-L94))

### P3. WAL のグループコミットとチェックポイントを検証する

別キーへの並列更新で `sync_data` が支配的と分かった場合、複数コミットを 1 回の WAL 書き込み・同期にまとめます。全コミットに一意で単調なバージョンを割り当て、WAL への追記、同期完了、読み手への公開、クライアントへの成功応答の順序を明確にします。バッチの上限は件数と待機時間の両方で制御し、単一接続の遅延を悪化させない値を実測で選びます。

実装前に失敗時の意味も修正対象にします。現行 `Transaction::commit` は WAL 追記より前に状態を `Committed` にし、アクティブ集合から除去します。さらに PGWire の暗黙トランザクション経路はコミット結果を捨てています。([transaction.rs](../crates/h2-mvstore/src/tx/transaction.rs#L362-L369), [server.rs](../crates/h2-server/src/server.rs#L225-L236)) 同期失敗時に成功を返さないこと、WAL クリア前にチェックポイントの永続化が確定していることをクラッシュ注入で確認します。`checkpoint` は全マップのルートをシリアライズして WAL を切り詰めるため、更新中に走る場合の遅延スパイクも別に計測します。([store.rs](../crates/h2-mvstore/src/store.rs#L201-L233))

### P4. 外部キーを伴う更新は索引で存在確認する

現在、子行の外部キー検証は親テーブルを全走査し、参照される親キーの更新は子テーブルを全走査します。([executor.rs](../crates/h2-sql/src/executor.rs#L3666-L3708), [同ファイル](../crates/h2-sql/src/executor.rs#L3828-L3882)) 対応するインデックスがあれば可視性付きの点検索・prefix scan を使い、なければ現行走査に戻します。変更前後で外部キー値が同じなら検証を省く条件も検討します。

**期待する方向:** この案は外部キーを持つ実アプリの更新に有効です。pgbench_accounts の単純な残高更新の主要改善には直結しません。参照アクション、NULL、複合キー、未コミット親子行で正しさを確認します。

## 実験の受け入れ条件

1. 同じデータ・SQL・同期設定・接続経路で変更前後を比較し、TPS だけでなく p95/p99 とエラー率を報告する。改善倍率は結果が出てから記載する。
2. 同一キーと分散キーを別グラフにし、行競合の上限と WAL / ツリー処理の上限を混同しない。
3. コミット成功後の再起動、書き込み途中の強制終了、同期エラー、長時間スナップショット、並列更新とチェックポイントの同時実行で、値と履歴の整合性を検証する。
4. P1・P2 は結果件数、更新値、インデックス内容、`RETURNING`、制約違反、ロールバックが現行経路と一致することを確認する。

実装順は **P0 → P1 → P2** を基本とし、P0 で WAL 同期が支配的と判明した場合は P3 を先にします。外部キーを多用するワークロードでは P4 を先行させます。
