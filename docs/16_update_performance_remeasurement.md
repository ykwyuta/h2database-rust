# UPDATE 性能の再測定と原因評価（2026-09-26）

本書は改善前の基準値を記録したもの。実装後の値は[実装結果](18_update_performance_implementation.md)を参照する。

## 結論

100 万行の主キー 1 行更新は、今回のローカル計測では永続化あり・単独実行で **2,409 TPS、中央値 0.384 ms** だった。サーバー側の平均実行時間 0.406 ms のうち、**WAL の `sync_data` が平均 0.343 ms（約 84%）** を占めた。同期を無効にする対照実験では 20,532 TPS となったが、コミット時の耐久性が異なるため、そのまま製品設定として採用できない。

4/8 並列にしても永続化ありの更新は約 2,500～2,700 TPS で頭打ちになる。全員が同じ行を更新すると行ロック待機が増え、8 並列では p99 が 43.241 ms だった。別々の行でも頭打ちが残るため、**行競合だけでなく、コミット全体を直列化する WAL 同期経路**が主要因である。さらに、100 万行の全量チェックポイントは 1 回約 0.5 秒、1 回につき約 136 MB をファイルに追記し、同時実行時の 4 並列更新を **2,541 → 1,526 TPS（約 40% 減）** に落とした。

## 測定条件と再現手順

Windows NT 10.0.26200.0、論理 CPU 16、Rust/Cargo 1.92.0、`--release` ビルド。基点コミットは `291bcb6` で、作業ツリーにはクエリ統計機能の未コミット変更が入っている。測定器は [`update_perf_probe.rs`](../crates/h2/examples/update_perf_probe.rs)。毎回一時ディレクトリに新規 DB を作り、`probe_accounts(aid INT PRIMARY KEY, abalance INT, filler VARCHAR)` を投入する。100 行単位で投入後、一度チェックポイントを作ってから測定した。単独・4・8 クライアントは、それぞれ 1 接続/スレッドで同じ SQL を繰り返す。`hot_update` は全員 `aid=1`、`distinct_update` はクライアントごとに別の `aid` を更新する。各条件の開始前にクエリ統計をリセットし、接続から見た TPS と p50/p95/p99、および `SHOW QUERY STATS` の区間別平均を記録した。エラーは全条件で 0 件。

PowerShell での再現例（ログは [`benchmarks/results`](../benchmarks/results/) に保存）：

```powershell
$env:PROBE_ROWS='1000000'
$env:PROBE_ITERS='1000'
$env:PROBE_SYNC='1'
$env:PROBE_PGWIRE='1'
$env:PROBE_CHECKPOINT='1'
cargo run --release -p h2 --example update_perf_probe
```

耐久性の対照実験は `PROBE_SYNC=0`、規模比較は `PROBE_ROWS=10000` / `100000` で実行する。`PROBE_PGWIRE=1` は `127.0.0.1` 上の PGWire 簡易プロトコルであり、Docker NAT や `pgbench` は通していない。PGWire のサーバー統計には各接続 10 回のウォームアップも含まれる。単独の `point_select` は更新処理ではなく検索コストの対照である。クエリ統計自体の測定負荷は差し引いていない。

## 100 万行・永続化ありの測定値

各クライアント 1,000 回。`engine` と待機の値はサーバー側の **1 呼び出し当たり平均 ms**。p 値はクライアント側の全呼び出しから計算した値で、平均時間と直接足し引きはできない。ローカル組み込み経路のログは [`1m-sync.txt`](../benchmarks/results/2026-09-26-update-probe-1m-sync.txt)。

| 負荷 | 並列 | TPS | p50 / p95 / p99 (ms) | engine (ms) | 行待機 (ms) | コミット待機 (ms) | WAL 同期 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 主キー SELECT | 1 | 91,585 | 0.011 / 0.013 / 0.020 | 0.007 | 0 | 0 | 0 |
| 同一行 UPDATE | 1 | 2,409 | 0.384 / 0.702 / 0.764 | 0.406 | 0 | 0 | 0.343 |
| 同一行 UPDATE | 4 | 2,541 | 1.058 / 3.961 / 9.480 | 1.461 | 0.666 | 0 | 0.347 |
| 別行 UPDATE | 4 | 2,572 | 1.432 / 2.323 / 3.171 | 1.545 | 0 | 0.223 | 0.356 |
| 同一行 UPDATE | 8 | 2,513 | 0.754 / 13.585 / 43.241 | 2.796 | 1.951 | 0 | 0.354 |
| 別行 UPDATE | 8 | 2,684 | 2.801 / 4.395 / 5.629 | 2.969 | 0 | 0.538 | 0.345 |

すべての更新で `point_gets/call=1`、`scan_entries/call=1`。主キー探索が全行走査に落ちている兆候はない。WAL 書き込みは単独更新で平均 0.012 ms、同期は 0.343 ms。単独更新では同期が実行時間の約 84%、書き込み本体は約 3% だった。

同じ新規 DB での PGWire ループバック結果は、主キー SELECT 1 並列が 8,297 TPS / p50 0.118 ms、同一行 UPDATE 1 並列が 1,834 TPS / p50 0.478 ms、同一行 UPDATE 4 並列が 2,540 TPS、別行 UPDATE 4 並列が 2,529 TPS だった。単独更新の組み込み経路との差は p50 で約 0.094 ms。通信・プロトコル処理も寄与するが、今回のローカル条件では WAL 同期より小さい。

## 対照実験とチェックポイント

| 条件 | 同一行 UPDATE 1 並列 | 同一行 UPDATE 4 並列 | 別行 UPDATE 4 並列 | チェックポイント時間 |
| --- | ---: | ---: | ---: | ---: |
| 1 万行、同期あり | 2,423 TPS / engine 0.402 ms | 2,413 TPS | 2,646 TPS | 10.2 ms |
| 10 万行、同期あり | 2,529 TPS / engine 0.386 ms | 2,555 TPS | 2,707 TPS | 50.3 ms |
| 100 万行、同期あり | 2,409 TPS / engine 0.406 ms | 2,541 TPS | 2,572 TPS | 541.4 ms |
| 100 万行、同期なし | 20,532 TPS / engine 0.043 ms | 22,686 TPS | 27,841 TPS | 2,687.0 ms |

規模比較の 1 万/10 万行は各クライアント 200 回、100 万行・同期ありは 1,000 回、同期なしは 200 回。各行のチェックポイント時間は全負荷終了後の 1 回であり、ストレージ I/O に揺らぎがある。生ログは [`10k-sync.txt`](../benchmarks/results/2026-09-26-update-probe-10k-sync.txt)、[`100k-sync.txt`](../benchmarks/results/2026-09-26-update-probe-100k-sync.txt)、[`1m-sync.txt`](../benchmarks/results/2026-09-26-update-probe-1m-sync.txt)、[`1m-no-sync.txt`](../benchmarks/results/2026-09-26-update-probe-1m-no-sync.txt)。同期なしでも終了時の `store.sync()` は実行しているが、各更新の成功応答前に WAL を同期しない。**8.5 倍の TPS 差は耐久性を変えた診断値であり、同等条件の性能改善ではない。**

100 万行で 4 並列・同一行更新中に 1 秒間隔の `sync()` を走らせた条件は 1,526 TPS、p99 18.800 ms。同期なしではなく永続化ありの通常更新 2,541 TPS から約 40% 低下した。2 回のチェックポイントの最長は 523.7 ms。DB の論理ファイル長は最初の 136,294,624 バイトから 2 回後 408,893,909 バイト、さらに終了時の 1 回後 545,193,530 バイトになった。ほぼ全量を毎回追記している。ファイルの物理割り当て量は測っていない。

## 原因の評価

1. **永続 WAL 同期が単独更新の主因。** [`WalManager::append`](../crates/h2-mvstore/src/wal.rs) は更新コミットごとに `sync_data()` を呼ぶ。実測 0.343 / 0.406 ms と同期無効時の差が一致する。別行の並列更新でも `MVStore::commit_wal` が `version.write()` を保持したまま WAL を書き、同期まで待つため、独立した行のコミットも直列化される。[`store.rs`](../crates/h2-mvstore/src/store.rs) の `commit_lock_ms` は別行 8 並列で平均 0.538 ms。`wal_lock_ms` が 0 に近いのは、先に version ロックで待つためである。ただし計測した待機区間の合計だけで並列時の全平均時間は説明し切れず、残差の細分化は未実施。
2. **同一行の競合は高パーセンタイル遅延を増やす。** [`Transaction::put`](../crates/h2-mvstore/src/tx/transaction.rs) は他トランザクションの未コミット値があると待つ。8 並列では同一行の行待機平均 1.951 ms、p99 43.241 ms。別行なら行待機は 0、p99 5.629 ms に下がる。しかし別行の TPS も 2,684 にとどまるため、行競合だけでは総スループットの上限を説明できない。[`point_update.sql`](../benchmarks/pgbench/point_update.sql) も全接続が同じ `aid=100` を更新する。
3. **全量チェックポイントが大規模 DB の更新を妨げ、ファイルを増やす。** [`MVStore::checkpoint`](../crates/h2-mvstore/src/store.rs) は version 書き込みロックの下で全マップのルートをシリアライズし、[`FileStore::append_and_commit`](../crates/h2-mvstore/src/file_store.rs) で新チャンクを追記して同期する。[`demo/002_psql`](../demo/002_psql/src/main.rs) は 1 秒ごとに `sync()` を呼び、それがチェックポイントになる。既存の `pgbench_1m.h2` は 2026-09-26 時点で論理サイズ約 406.8 GB だった。全量追記の反復と整合するが、そのファイルの履歴を検証していないため、サイズの全量をこの仕組みだけに帰属させない。
4. **今回の単一行更新では、100 万行化による検索コスト増は主因ではない。** 1 万～100 万行で単独更新の engine 平均は 0.386～0.406 ms、各更新の point get と scan entry はともに 1 回だった。CPU 側の MVCC/CoW/SQL 処理は残るが、同期ありの単独更新では約 0.06 ms 以下の差分に含まれる。CPU コストの詳しい内訳は未測定。

## 既存の pgbench 評価との関係と次の改善

[既存の scale 10 レポート](12_pgbench_performance_evaluation.md)の H2 値は同一行更新で 1 接続 168.67 TPS / 5.93 ms、4 接続 373.65 TPS / 10.70 ms だった。今回の値との差は、PGWire の接続経路（以前は Docker NAT、今回はループバック）、DB の状態、チェックポイント負荷、SQL/スキーマ、試験時間、作業ツリーの違いが混ざる。**同一条件の改善倍率とは解釈できず、以前の遅さの個別要因も断定できない。** PostgreSQL と Java 版 H2 は今回は再測定していないため、相対性能の優劣も更新しない。

改善の優先順位は、(1) チェックポイントを差分化し、1 秒ごとの全量スナップショットとファイル増大を解消する、(2) コミット順序・可視性・失敗時の応答を明確にした上で別行更新のグループコミットを検討する、(3) 同一行のロック待機と CPU 側の二重 CoW を細分化して最適化する、の順が妥当である。グループコミットは並列更新の同期回数を減らせる可能性があるが、単独更新の同期待ちには効きにくい。`H2_SYNC_COMMIT=0` を性能改善策として扱わない。変更後は同じスキーマ・接続経路・同期設定で TPS、p95/p99、WAL 同期時間、ファイル増加量を比較し、クラッシュ後の整合性も検証する。
