# PostgreSQL pgbench 性能評価レポート (h2database-rust)

## 1. 概要
PostgreSQL の標準ベンチマークツールである `pgbench`（バージョン 17.11）を用いて、`h2database-rust` の PostgreSQL ワイヤプロトコル（PGWire）サーバーに対する性能計測およびスループット（TPS: Transactions Per Second）/応答レイテンシの評価を実施しました。

---

## 2. 計測環境
- **DB エンジン**: `h2database-rust` (PGWire サーバー、Release 最適化プロファイル)
- **接続プロトコル**: PostgreSQL Wire Protocol (3.0 互換、Simple Query モード)
- **テスト対象データ**: `pgbench` 標準スケール 1 ( accounts: 10,000 件、branches: 1 件、tellers: 10 件、history: 0 件 )
- **クライアント**: Docker (`postgres:17-alpine`) 上の `pgbench` 17.11

## 4. ボトルネック分析と最適化

### 4.1 発見されたボトルネック
当初の計測において、`SELECT 1` や単一行検索などの軽量クエリであっても **1トランザクションあたり約 3.4 秒（約 0.31 TPS）** という著しい遅延が発生していました。

#### 原因分析
- MVCC トランザクションのコミット処理（`crates/h2-mvstore/src/tx/transaction.rs` の `commit()`）において、データ変更の有無にかかわらず無条件で `self.store.mvstore().commit()` が呼び出されていました。
- `mvstore.commit()` は全マップ（10,000件の accounts テーブル含む）の B+Tree 全ノードを JSON シリアライズし、物理ストレージファイルへ追記コミットを行うため、読み取り専用クエリであってもクエリごとに巨大なシリアライズとディスク I/O が同期的に発生していました。

### 4.2 実施した最適化
`commit()` 時に UndoLog（変更ログ）が空（`undo_logs.is_empty()`）である場合、データ変更が発生していない「読み取り専用トランザクション」と判定し、ストレージへの物理追記コミットをバイパスするよう改修しました。

```rust
let has_changes = !undo_logs.is_empty();
// ...
if has_changes {
    self.store.mvstore().commit()?;
}
```

### 4.3 最適化効果
- 単一行検索の平均レイテンシ: **3,436 ms → 9.45 ms（約 360 倍の高速化）**
- スループット: **0.31 TPS → 105.81 TPS（c=1） / 739.37 TPS（c=8）**

## 5. 評価と考察
1. **高い並行スケーラビリティ**:
   - Point Select において、並行クライアント数を 1 → 4 → 8 と増加させるにつれて、スループットが **105.8 TPS → 390.1 TPS → 739.4 TPS** とほぼ線形にスケールしました。
   - レイテンシも 9.45ms（c=1）から 10.82ms（c=8）とほぼ劣化せず、Tokio 非同期ランタイムと MVCC 読み取り分離の並行性が効果的に機能しています。
2. **分析・集約クエリ（OLAP）の高速性**:
   - 10,000行の全表集約クエリ（COUNT, SUM, AVG）が 1クエリあたり約 24ms（4並行時 150 TPS）で高速に完了しました。Arrow 互換のベクトル化/バッチ処理パイプラインの恩恵が現れています。
3. **書き込みトランザクションの特性と今後の展望**:
   - 現在のストレージ永続化設計では、更新コミット時にツリーメタデータをディスクへ同期追記するため、Point Update のレイテンシは約 220ms となっています。
   - 今後の更なる高速化として、先行書き込みログ（WAL: Write-Ahead Logging）方式の導入やグループコミット（複数トランザクションのコミットをバッチ化して一括 fsync）を採用することで、書き込みスループットを数十〜数百倍向上させることが可能です。
