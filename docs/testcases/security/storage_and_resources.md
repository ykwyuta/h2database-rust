# 永続化・可用性・情報漏えいテストケース

共通の準備と判定方法は [README](README.md) を参照。ファイルの改変は一時 DB のコピーに限定し、原本には行わない。`H2_SYNC_COMMIT=1` で耐久化を有効にして実施する。

## DATA-01 WAL 末尾の切断・CRC 不一致（P0）

- 手順: 正常な 2 コミット後にプロセスを停止し、WAL コピーの末尾に部分レコード、CRC 不一致レコードをそれぞれ付ける。再オープン後にもう 1 件コミットし、再々オープンする。
- 合格基準: 完全な 2 件を復旧し、不完全な末尾だけを捨てる。新しいコミットを再々起動後も失わない。

## DATA-02 WAL レコード長の改ざん（P0）

- 手順: WAL コピーの先頭レコード長を `0`、`0xffffffff`、実ファイル長を超える値へ変更して開く。実ファイルサイズとピークメモリを記録する。
- 合格基準: 境界外長を有限のメモリ・時間で拒否または安全に切り詰める。panic や大規模確保、既存の確定済みデータの改変がない。

## DATA-03 二重ヘッダの片側破損（P0）

- 手順: チェックポイント後の DB コピーで、先頭ヘッダだけ、シャドウヘッダだけの CRC または magic を壊して、それぞれ再オープンする。
- 合格基準: 片側が有効なら、最後に耐久化された内容を復旧する。破損側を無条件に採用しない。

## DATA-04 両ヘッダ・差分チャンクの破損（P0）

- 手順: 両ヘッダ破損、最新差分の CRC 破損、差分の前チャンク参照先をファイル外へ変更、循環参照の 4 パターンで再オープンする。
- 合格基準: 各破損を明示的エラーとして検出する。無限ループ、任意ファイル読み取り、panic、成功に見える不完全データがない。

## DATA-05 チェックポイント・ファイル置換中の強制停止（P0）

- 手順: WAL 同期直後、差分追記直後、ヘッダ片側書き込み直後、容量回収の旧ファイル退避直後に故障注入してプロセスを停止し、DB を再オープンする。
- 合格基準: 成功応答済みのコミットは失われず、未確定の変更は現れない。旧ファイルとバックアップの選択が一貫し、再起動後に書き込みを継続できる。

## DATA-06 ディスク容量不足・書き込み失敗（P0）

- 手順: テスト用ファイルシステムで WAL 追記、`sync_data`、差分書き込み、ヘッダ同期、ファイル置換を個別に失敗させる。失敗したトランザクションと成功応答済みのトランザクションを再起動後に調べる。
- 合格基準: 失敗を成功として返さず、コミット境界が守られる。ロックが解放され、再起動時のデータは確定済みの集合と一致する。

## DATA-07 競合と資源枯渇（P1）

- 手順: 別行への同時更新、同一行で待機する更新、多数の `SELECT`、チェックポイントを重ね、同時接続数と行数を段階的に増やす。タイムアウト後にも正常要求を送る。
- 合格基準: メモリと待機スレッドが設定上限内に収まり、タイムアウト後にロックが残らない。デッドロック、無期限待機、二重コミットがない。

## DATA-08 クエリ統計とエラーの秘密情報（P1）

- 手順: テスト用の識別文字列を SQL 文字列リテラルとパスワード引数に入れ、成功・構文エラーを発生させる。`SHOW QUERY STATS`、MCP の `get_table_statistics`、PGWire のエラー応答、サーバーログを確認する。
- 合格基準: 一般ユーザーに統計を公開せず、統計・エラー・ログにパスワードやリテラルの原文を残さない。統計のリセット権限も維持される。
