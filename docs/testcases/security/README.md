# セキュリティテストケース

このディレクトリは、現行の組み込み API、PGWire、MCP HTTP、永続化処理でセキュリティ上の問題を検出するための**未実行のテスト仕様**です。合格を確認した記録ではありません。実装が未対応でも期待結果を緩めず、失敗として記録します。

## 共通の実行条件

1. テストごとに新しい一時ディレクトリと DB を作り、外部から接続するサーバーは `127.0.0.1:0` にバインドする。`demo/002_psql` は `0.0.0.0` にバインドするため、隔離せずに起動しない。
2. `public_data(id INT PRIMARY KEY, value VARCHAR)` と `secret_data(id INT PRIMARY KEY, value VARCHAR)` を作り、両方に識別可能な 1 行を入れる。一般ユーザー `reader` には `public_data` の `SELECT` のみを付与する。テスト用パスワードは固定のダミー値とし、実在の秘密は使わない。
3. 各ケースの前後で表の行、スキーマ、ユーザー一覧、DB と WAL のサイズを記録する。拒否が期待される操作では、エラー応答だけでなく**状態が変わっていないこと**を確認する。
4. ネットワーク異常系は接続単位で 3 秒以内に終了させ、続けて正常な `SELECT 1` を実行してサーバーの生存を確認する。サイズ・時間の上限は実装の設定値がある場合はその値を用いる。
5. 判定は `PASS` / `FAIL` / `BLOCKED` / `NOT RUN` で記録し、実行日、コミット ID、OS、起動設定、入力、観測結果を残す。既存の単体テストが同じ経路を一部確認していても、ここで指定した攻撃入力を実行するまでは `PASS` としない。

優先度 `P0` は認証回避、権限昇格、未認証の書き込み、メモリ枯渇、永続データの破壊を検出するケース、`P1` は情報漏えい、耐障害性、資源制限を確認するケースです。

## 静的確認で見つかった重点箇所

- `AuthManager::new` は複数のパスワードなし管理者を作成する。PGWire は TLS 要求に `N` を返し、パスワードがある場合も平文認証を要求する。
- SQL 実行層では `CREATE USER`、`GRANT`、`BACKUP TO` などの独自コマンドが通常の文別権限確認より前に処理される。
- MCP HTTP は現時点で認証ミドルウェアが見えず、CORS は permissive。`query_read` の判定は先頭語中心で、`EXPLAIN ANALYZE` や複数文を含む入力を検査する必要がある。
- PGWire はクライアント申告のフレーム長でバッファを確保する。保存形式には CRC と二重ヘッダがあるが、破損・巨大な長さ・復旧時の境界値を検証する必要がある。

これらはコード調査から立てた検証仮説です。各ケースの観測結果や脆弱性の確定結果ではありません。
