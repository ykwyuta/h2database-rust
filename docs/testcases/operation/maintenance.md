# VACUUM・断片化・容量（MAINT）

共通のデータ、計測、判定は [README](README.md) を参照。H2 Rust の `VACUUM` は現状ファイル再構築に対応するため、PostgreSQL の通常 `VACUUM` と同一の内部動作は要求しない。

## MAINT-01 手動 VACUUM の論理正しさと容量回収（P0）

- 手順: 追加・更新・削除を繰り返し、DB と WAL の合計サイズを採る。`VACUUM` 後に行数、値、索引結果、ファイルサイズを比較し、再起動して再確認する。
- 合格基準: コミット済みデータを保ち、不要領域を回収する。サイズが減らない場合は回収不能理由を説明できる。

## MAINT-02 長寿命トランザクションと読取スナップショット（P0）

- 手順: セッション A が古いスナップショットを保持し、B が更新・削除する。C で `VACUUM` し、A/B/C の読み取りと再起動結果を照合する。
- 合格基準: A の可視性と B の確定結果を壊さず、回収できない版は保留するか安全に拒否する。スナップショット破壊を成功として返さない。

## MAINT-03 保守中の書き込み遅延（P0）

- 手順: 100 万行 DB の `VACUUM` とチェックポイント履歴回収を別々に実行し、並行する別行更新の TPS・p99・最大待機時間を採る。中断・再試行も行う。
- 合格基準: 保守の停止時間と書き込みへの影響を測定でき、設定した業務 SLA 内に収まる。中断後も DB を開き続けられる。

## MAINT-04 断片化・無駄領域の診断（P1）

- 手順: 無作為順の挿入、範囲削除、同一キー更新を行う。表/索引またはストア単位の生存データ量、回収可能バイト、差分深さ、走査 I/O を保守前後で記録する。
- 合格基準: どこに空間と性能の損失があるかを測れる。対象・時期を判断する情報があり、ファイル全体サイズだけに頼らない。

## MAINT-05 自動保守と閾値（P1）

- 手順: 更新量、WAL サイズ、経過時間を段階的に増やし、チェックポイント、容量回収、統計更新、不要版回収の発火・不発火と各実行履歴を確認する。
- 合格基準: 必要な保守が有界な遅延で自動実行される。閾値や実行時間帯を制御でき、無変更時は不要な再書き込みをしない。

## MAINT-06 失敗時の復旧と余裕容量（P0）

- 手順: `VACUUM`/履歴回収中のディスク不足、同期失敗、ファイル置換直後の強制終了を一時 DB で再現する。旧ファイル・一時ファイル・バックアップを調べる。
- 合格基準: 成功応答済みのコミットを失わず、再起動後に単一の正しい版を選べる。必要な一時容量と失敗理由が運用者に示される。
