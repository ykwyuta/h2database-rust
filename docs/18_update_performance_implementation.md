# UPDATE 性能改善の実装結果（2026-09-26）

## 実装した変更

[改善案](17_update_performance_improvement_plan.md)の P0～P3 と、P4 の小さな割り当て削減を実装した。変更前の条件・数値は[再測定報告](16_update_performance_remeasurement.md)、変更後の生ログは [`2026-09-26-update-after-1m-final.txt`](../benchmarks/results/2026-09-26-update-after-1m-final.txt) を参照する。

| 項目 | 実装内容 |
| --- | --- |
| P0 チェックポイント制御 | `sync_wal()` とチェックポイントを分離した。デモサーバーは毎秒 WAL を同期し、WAL 16 MiB または前回から 60 秒に達した場合だけ変更のある DB をチェックポイントする。同期 I/O は `spawn_blocking` で実行する。 |
| P1 差分保存と容量回収 | 初回は従来の全量チャンクを保存し、以後はマップの変更キー・削除・全消去とマップの追加/削除を CRC 付き差分チャンクとして追記する。再起動時は全量チャンクから差分を順に再生する。64 差分後に現在の全量スナップショットへまとめ、古い領域を回収する。既存の全量チャンク形式は読める。 |
| P2 WAL グループコミット | コミット版を一意に割り当て、未コミット値から WAL レコードを作る。別行の要求を短くまとめて 1 回同期し、同期成功後に確定値を公開・成功応答する。同期失敗時は未コミット値をロールバックする。物理同期時間 `wal_sync_ms` と、各要求の確定待ち `wal_durable_wait_ms` を分けた。 |
| P3 行待機通知 | トランザクション終了時の全待機者への一斉通知を、終了したトランザクションを待つスレッドへの通知に変えた。通知と待機開始の競合では、状態フラグとアクティブ状態の再確認で通知を失わない。 |
| P4 CPU 側 | `RETURNING` のない UPDATE では更新済み行を結果用配列に保持しない。二重 CoW 自体の削減は含まない。 |

保存形式の差分単位は**変更キー**であり、[元の提案](17_update_performance_improvement_plan.md)に書いたページ単位の永続化とは実装方式が異なる。今回の対象である少数行更新では全マップ再シリアライズを避けられるが、1 回のチェックポイントまでに多数のキーを更新すれば、そのキー数に比例して書き込む。容量回収時は全量スナップショットを作るため、その間は書き込みを止める。

## 同一条件での再測定

100 万行、`--release`、コミットごとの耐久化あり、各クライアント 1,000 回。組み込み経路の TPS と p99 は以下のとおり。変更前後とも新規一時 DB と同じ測定器を使ったが、別実行なのでストレージ I/O の揺らぎはある。すべてエラー 0 件。

| 負荷 | 変更前 TPS | 変更後 TPS | 変更前 p99 | 変更後 p99 |
| --- | ---: | ---: | ---: | ---: |
| 同一行 UPDATE、1 並列 | 2,409 | 2,383 | 0.764 ms | 0.744 ms |
| 同一行 UPDATE、4 並列 | 2,541 | 2,159 | 9.480 ms | 4.617 ms |
| 同一行 UPDATE、8 並列 | 2,513 | 2,102 | 43.241 ms | 13.844 ms |
| 別行 UPDATE、4 並列 | 2,572 | 3,846 | 3.171 ms | 1.552 ms |
| 別行 UPDATE、8 並列 | 2,684 | 7,254 | 5.629 ms | 1.669 ms |

別行 8 並列は約 **2.70 倍**の TPS、p99 は約 **70% 減**。同一行は p99 が下がった一方、4/8 並列の TPS は約 **15～16% 低下**した。同一キーはグループ化しにくく、確定後の値公開と待機通知のコストが増えたことが考えられるが、内訳の追加計測なしに各要因の寄与率は断定できない。

100 万行の同時実行チェックポイントは、変更前に 2 回中の最長 **523.7 ms**、変更後は **6.0 ms**。変更前は 1 回につき約 **136 MB** を追記した。変更後は 2 回合計で **12,858 バイト**、終了時の次の 1 回で **1,494 バイト**の追記だった。変更後の同時実行中・同一行 4 並列 UPDATE は 2,312 TPS（変更前 1,526 TPS）。この比較にはグループコミットと行通知の変更も含むため、チェックポイントだけの効果量ではない。

PGWire ループバックの別行 UPDATE は、4 並列 **2,529 → 3,410 TPS**、8 並列 **2,503 → 6,012 TPS**。Docker NAT 経由の以前の pgbench や PostgreSQL 本体は今回再測定していない。

`wal_sync_ms` は代表スレッドが実行した物理同期の合計を呼び出し数で割った値となり、別行 8 並列では **0.052 ms/呼び出し**だった。`wal_durable_wait_ms` は全要求の確定待ちで、同条件では **0.823 ms/呼び出し**。両者は別の意味を持ち、単純に足さない。なお、変更前のログには `wal_durable_wait_ms` 列がない。

## 検証と残る課題

- `cargo test --workspace --quiet` とデモサーバーの `cargo check` が通過した。差分チャンクの再起動、WAL 復旧後の差分作成、マップの改名/消去/削除、容量回収後の再起動、8 スレッドのコミット番号順序、更新とチェックポイントの同時実行をテストした。WAL 末尾破損時の切り詰めと、ファイル置換途中で残ったバックアップの復元も確認した。
- 同一行更新の TPS 回帰がある。ここを改善する際も、別行の TPS と p99、コミット順序、耐久性を同じ条件で再測定する。
- ディスク書き込み失敗や電源断を全命令境界で注入した試験は未実施。ヘッダの書き込み途中で電源断した場合の二重ヘッダによる復旧も未実装である。新しい保存形式を本番データへ適用する前に、強制終了・I/O エラー注入と旧形式からの移行試験が必要。
- 全量ファイル置換による容量回収は書き込みを停止させる。64 差分という閾値は初期値であり、更新量・WAL 容量・復旧時間・遅延スパイクを長時間測って調整する。
- P4 の二重 CoW 削減は未実装。同期ありの単独更新では物理 WAL 同期が主要因であり、CPU 側の効果を区間別に計測してから設計を変更する。
